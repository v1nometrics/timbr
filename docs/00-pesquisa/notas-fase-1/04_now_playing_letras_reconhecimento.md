# Now Playing, multi-session control, audiophile metadata, visualization, lyrics and music recognition for a macOS notch app (as of 2026-11-21)

Scope note: research done on 2026-11-21. One local check was run on this machine (macOS 26.6, build 25G72): the AppleScript dictionaries (`.sdef`) of Music.app and Spotify.app were read directly. Those findings are labeled "[local sdef inspection]". GitHub license, star and last-push data come from the GitHub API on 2026-11-21. EQ, device control, sample-rate switching and audio routing are out of scope (other researchers cover them). Process taps are mentioned only as the input for visualization and recognition.

## 1. Now Playing: MediaRemote, its lockdown, public alternatives, Live Activities, and multiple simultaneous sessions

### Takeaway
macOS still has no public API to read or control other apps' playback. Since macOS 15.4 every serious third-party app (boring.notch, Music Presence, Lyrimuse and others) gets this through ungive/mediaremote-adapter (BSD-3-Clause). It runs MediaRemote inside `/usr/bin/perl`, which carries an Apple bundle ID, and has been tested on macOS 27.0. As of Nov 2026 you can READ every playing session separately with private calls (merged as `get --bundle-id`, tested on macOS 27), but there is still no safe way to send a COMMAND to a session that isn't the elected one. The macOS 27.3 developer beta (expected in December 2026) adds native menu-bar Live Activities for Apple Music and other Apple apps, and says third-party Mac apps can adopt them. Nothing shows that third-party music players publish through them yet.

### Cited Findings
**MediaRemote lockdown and how the adapter gets around it**
- mediaremote-adapter was created because "the MediaRemote framework being completely non-functional when being loaded directly from within an app, starting with macOS 15.4" — [ungive/mediaremote-adapter README](https://github.com/ungive/mediaremote-adapter)
- How it works: "using a system binary – `/usr/bin/perl` in this case – which is entitled to use the MediaRemote framework and by dynamically loading a custom helper framework that prints real-time updates to stdout." The reason it works: "processes with a bundle identifier starting with `com.apple.` are granted permission to access the MediaRemote framework. The Perl platform binary `/usr/bin/perl` is reported as having the bundle identifier `com.apple.perl` (or a variation)". The mediaremoted log shows `bundleIdentifier = com.apple.perl5` — [README](https://github.com/ungive/mediaremote-adapter)
- License: BSD-3-Clause. 311 stars, last push 2026-11-20. The README badge says "macOS 27.0 (26A5425a)", last tested Fri Sep 4 2026 — [GitHub API / README](https://github.com/ungive/mediaremote-adapter)
- Integration model: you bundle `mediaremote-adapter.pl`, `MediaRemoteAdapter.framework` (bundled but "*not linked against*") and optionally `MediaRemoteAdapterTestClient`, then call `/usr/bin/perl /path/mediaremote-adapter.pl /path/MediaRemoteAdapter.framework COMMAND`. Builds are universal x86_64/arm64 — [README](https://github.com/ungive/mediaremote-adapter)
- Commands: `get`, `stream` (JSON lines; diffing on by default; `--debounce=N`, `--no-diff`, `--micros`, `--now`, `--no-artwork`, `--allow-missing-title`), `send` (IDs 0–13: play, pause, toggle, stop, next, previous, toggle shuffle/repeat, start/end seek, ±15 s), `seek POSITION` (µs), `shuffle`, `repeat`, `speed`, `test` — [README](https://github.com/ungive/mediaremote-adapter)
- Metadata keys: `bundleIdentifier`, `parentApplicationBundleIdentifier`, `playing`, `title`, `artist`, `album`, `duration`, `elapsedTime`, `timestamp`, `artworkMimeType`, `artworkData`, `composer`, `genre`, `isAdvertisement`, `isLiked`, `isMusicApp`, `playbackRate`, `queueIndex`, `radioStationIdentifier`, `repeatMode`, `shuffleMode`, `trackNumber`, `totalTrackCount`, `uniqueIdentifier`, `contentItemIdentifier`, `mediaType`, and others. There are NO codec, sample-rate, bit-depth or bitrate keys. Artwork "often takes a bit of time to load"; the stream command re-uses artwork that briefly unloads during seeks — [README](https://github.com/ungive/mediaremote-adapter)
- Built-in workaround for TIDAL: `--experimental-peculiar-debounce:com.tidal.desktop=1000`, because TIDAL reports metadata that mixes the previous and next track — [README](https://github.com/ungive/mediaremote-adapter)
- The `test` command briefly creates a fake now-playing entry to check that the adapter still works, so an app can "fall back to other methods for media detection (e.g. AppleScript), since future macOS updates may break MediaRemote access again" — [README](https://github.com/ungive/mediaremote-adapter)
- Before the adapter, `osascript` with `MRNowPlayingRequest` was an option, but it "is unable to load the song artwork and it is impossible to get real-time updates" — [README](https://github.com/ungive/mediaremote-adapter)
- Apps that use it: Music Presence (Discord status, since v2.3.1), media-control (CLI, `brew install media-control`), Aerial screensaver, Lyrimuse, Peak Hold Bar, Now Playing Display (ESP32) — [README](https://github.com/ungive/mediaremote-adapter); [issue #47](https://github.com/ungive/mediaremote-adapter/issues/47)
- There is a maintained Swift Package fork, ejbills/mediaremote-adapter (BSD-3-Clause, 57 stars, last push 2026-11-04) — [README note](https://github.com/ungive/mediaremote-adapter); [ejbills/mediaremote-adapter](https://github.com/ejbills/mediaremote-adapter)
- ungive/media-control (the CLI) has no license file according to the GitHub API (`license: none`), so you cannot legally vendor it as-is — [ungive/media-control](https://github.com/ungive/media-control)
- The older kirtan-shah/nowplaying-cli (GPL-3.0) is one of the tools that broke in 15.4 — [nowplaying-cli issue #28 linked in README](https://github.com/kirtan-shah/nowplaying-cli/issues/28)

**Multiple simultaneous sessions (Spotify + browser tab, etc.)**
- In Sept 2025 the maintainer said: "from what I know there can only be one now playing application and you can't access the current state of other apps" — [issue #25](https://github.com/ungive/mediaremote-adapter/issues/25) (older information, now superseded for reading)
- On macOS 27.0, a contributor showed that reading other sessions works: `MRMediaRemoteGetNowPlayingClients(queue, ^(NSArray *clients))` lists every registered client, `MRNowPlayingPlayerPathCreate(MRMediaRemoteGetLocalOrigin(), client, nil)` builds a player path for one client, and `MRMediaRemoteGetNowPlayingInfoForPlayer(path, …)` returns that client's full now-playing dictionary — [issue #41](https://github.com/ungive/mediaremote-adapter/issues/41)
- This shipped as `get --bundle-id=ID`, which returns an array of every session whose `bundleIdentifier` or `parentApplicationBundleIdentifier` matches. "More than one application can match, since applications may play media through a shared helper process. For example, Safari and Orion both play through `com.apple.WebKit.GPU`." Per-player playback state comes from `MRMediaRemoteGetPlaybackStateForPlayer`. Artwork is included because the second argument of `GetNowPlayingInfoForPlayer` is an `includeArtwork` flag. It was tested on macOS 27 / Apple silicon; Intel and older macOS were not tested — [README](https://github.com/ungive/mediaremote-adapter); [PR #42](https://github.com/ungive/mediaremote-adapter/pull/42)
- Two Orion instances playing at once showed up as two separate entries under `com.apple.WebKit.GPU`, each with its own `parentApplicationBundleIdentifier` and `processIdentifier` — [issue #41 comment](https://github.com/ungive/mediaremote-adapter/issues/41)
- Targeted COMMANDS do not work. "`MRMediaRemoteSendCommandToPlayer` and `MRMediaRemoteSendCommandToApp` with A's player path still reach B", because the daemon gets an unresolved path and falls back to the elected player. A workaround using `MRMediaRemoteSetNowPlayingApplicationOverrideEnabled` / `MRMediaRemoteSetOverriddenNowPlayingApplication` was withdrawn as unsafe: "it changes system-wide state and can redirect commands from unrelated processes… a killed process can leave it active." The maintainer closed PR #43 because it "influences other processes that interact with MediaRemote" — [issue #41](https://github.com/ungive/mediaremote-adapter/issues/41); [PR #43](https://github.com/ungive/mediaremote-adapter/pull/43)
- Streaming all sessions is not implemented. `kMRMediaRemoteNowPlayingInfoDidChangeNotification` only fires for the elected app. For non-elected apps it does not fire on position changes or pause, so a multi-session stream would need polling `getNowPlayingClients` — [issue #41, maintainer comment](https://github.com/ungive/mediaremote-adapter/issues/41)
- Open PR/issue #46 proposes exposing the native `MPRemoteCommandCenter.likeCommand` state (`likeCommandEnabled`/`likeCommandActive`), tested on macOS 27 — [issue #46](https://github.com/ungive/mediaremote-adapter/issues/46)

- boring.notch (GPL-3.0, 11.4k stars, last push 2026-11-20) bundles the mediaremote-adapter binaries and launches `/usr/bin/perl` with `[scriptURL.path, frameworkPath, "stream"]`. It also has per-app controllers: `AppleMusicController` and `SpotifyController` (AppleScript `tell application "Music"/"Spotify"`, used for volume and favorite) and a `YouTubeMusicController` that talks HTTP to `http://localhost:26538` with bundle ID `com.github.th-ch.youtube-music` (the Pear Desktop API Server plugin) — [boring.notch NowPlayingController.swift](https://github.com/TheBoredTeam/boring.notch/blob/main/boringNotch/MediaControllers/NowPlayingController.swift); [YouTubeMusicModels.swift](https://github.com/TheBoredTeam/boring.notch/tree/main/boringNotch/MediaControllers); [GitHub API](https://github.com/TheBoredTeam/boring.notch)

- Pear Desktop (formerly th-ch/youtube-music) is MIT, 34.1k stars. Its API Server plugin has to be turned on in Plugins → API Server, and the port 26538 used by clients is the default — [pear-devs/pear-desktop](https://github.com/pear-devs/pear-desktop); [simple-bar YouTube Music docs](https://www.jeantinland.com/toolbox/simple-bar/documentation/youtube-music/); [Songify wiki](https://github-wiki-see.page/m/songify-rocks/Songify/wiki/Pear-YouTube-Music)
- Sleeve (Replay Software, closed source, paid): "Sleeve only works with the following music apps: Apple Music, Spotify, Doppler… will not work with the web player versions". It uses AppleScript ("not all apps support AppleScript, which Sleeve currently uses to fetch information and control playback") and needs the Automation permission. Current Sleeve "requires macOS 26 Tahoe or later". A legacy 2.3.5 build for macOS 11 to 26 is available on request. There is a developer integration guide for apps that want Sleeve support — [replay.software/help/sleeve](https://replay.software/help/sleeve); [troubleshooting](https://replay.software/help/sleeve/troubleshooting)
- A search snippet says Sleeve's troubleshooting page states "Apple Music in macOS Tahoe breaks the API Sleeve uses to query the Music app", so it can't get the current track when that track isn't in the user's library. Both a fetch and a text grep of the page failed to find that text, so treat it as unverified — [search result for replay.software troubleshooting](https://replay.software/help/sleeve/troubleshooting)
- Lyrimuse (GPL-3.0, 447 stars, last push 2026-11-20) is a hybrid. "Apple Music, Spotify and Kaset are read with Automation access. QQ Music, NetEase Cloud Music, Kugou Music, Kuwo Music, Soda Music, KKBOX, Amazon Music and LX Music are read through macOS's MediaRemote". Browser players (YouTube Music, Spotify Web) work after "Pair your browser once" — [Yudaotor/lyrimuse](https://github.com/Yudaotor/lyrimuse)
- NepTunes: the only GitHub repo found is beschoenen/NepTunes ("Last.fm scrobbler for iTunes and Spotify"). It has no license file and its last push was 2019-04-14, so it is effectively abandoned — [GitHub search](https://github.com/beschoenen/NepTunes)
- Producer-side reference: souvlaki (MIT, Rust) is a cross-platform media-controls library that publishes to MPNowPlayingInfoCenter / MPRemoteCommandCenter. A PR adds like-command support — [Sinono3/souvlaki](https://github.com/Sinono3/souvlaki); [issue #46](https://github.com/ungive/mediaremote-adapter/issues/46)

**Public alternatives and Live Activities**
- The adapter README notes that "macOS is the only operating system that does not have a public API for accessing metadata and controlling media playback" and asks Apple for an entitlement — [README](https://github.com/ungive/mediaremote-adapter)
- macOS Tahoe 26 shows Live Activities from a nearby iPhone in the Mac menu bar (a relay through iPhone Mirroring). A setting, "Allow Live Activities from iPhone", controls it — [Apple macOS Tahoe features PDF](https://www.apple.com/au/os/pdf/All_New_Features_macOS_Tahoe_Sept_2025_AU_Final.pdf); [Gadget Hacks](https://apple.gadgethacks.com/news/macos-273-live-activities-on-older-macs-whats-confirmed/)
- The macOS 27.3 developer beta 1 (reported 2026-11-04) "enables Live Activities for apps like Apple Music, Clock, and Voice Memos in the macOS menu bar" (Macworld also names Screen Recording). "Third-party Mac apps can also implement Live Activities support now." Release is expected in December — [MacRumors 2026-11-04](https://www.macrumors.com/2026/11/04/macos-27-3-live-activities-in-menu-bar/)
- Coverage reports that the new OLED MacBook Pro "replaces the notch with a pill-shaped Dynamic Island cutout". On other Macs, Live Activities appear as "small ovals positioned to the left of the menu bar icons". "No third-party app has shown up in current coverage" — [Gadget Hacks summarizing Macworld/MacRumors](https://apple.gadgethacks.com/news/macos-273-live-activities-on-older-macs-whats-confirmed/)

### Inferences
- Recommended architecture: (a) mediaremote-adapter `stream` for the elected session, which gives real-time metadata, artwork and commands; (b) poll `get --bundle-id=<id>` (or the private client-enumeration calls directly) every 1–2 s to build a list of all active sessions; (c) for control of non-elected sessions, use per-app channels where they exist (AppleScript for Music/Spotify/Doppler/VOX/Audirvana/Swinsian, HTTP for Pear Desktop and Roon, a browser extension for tabs). Otherwise you can only offer "bring to front / make active", not play/pause.
- Distribution: the approach runs `/usr/bin/perl` and loads a private framework, and every reference app ships outside the Mac App Store. Plan for Developer ID + notarization. A sandboxed App Store build is very unlikely to work. This is inferred, not tested.
- License compatibility: BSD-3 (adapter) works with any license. Copying code from boring.notch, Lyrimuse or LosslessSwitcher (GPL-3.0) requires the notch app to be GPL-3.0 as well. LyricsX/LyricsKit (MPL-2.0) is file-level copyleft.
- Live Activities on macOS 27.3 may be a channel for the notch app itself to publish (for example a recognition result), not a way to read other players. It also means the notch area on new OLED MacBook Pros will be shared with a system Dynamic Island, a design risk to watch.
- The adapter's `--bundle-id` reading has only been tested on macOS 27 / Apple silicon, so on 26.x it needs runtime feature detection with a fallback to elected-only.

### Gaps
- No ActivityKit-for-macOS developer documentation was found. It is unclear whether Music's macOS 27.3 Live Activity shows other apps' playback, and whether a third-party app can read other apps' Live Activities (almost certainly not, but not confirmed).
- No public Apple statement on whether MediaRemote access will be closed further (for example, blocking `com.apple.perl5`) in macOS 27.x or later.
- Whether the Mac App Store review would reject a bundled Perl and private-framework helper was not tested.
- No source found on how Alcove, NotchNook, DynamicLake or other closed-source notch apps get now-playing data on 15.4+.

## 2. Per-player integrations and audiophile metadata (codec, sample rate, bit depth, Hi-Res/Atmos flags)

### Takeaway
No system channel exposes the real stream format. MediaRemote has no format keys, and Spotify's AppleScript has none either. The Music.app AppleScript dictionary does define `sample rate` (Hz) and `bit rate` (kbps) on tracks. LosslessSwitcher reads Apple Music's real-time stream format by parsing unified logs (`OSLogStore`) from the Music process (`asbdSampleRate`, ALAC decoder "Input format", CoreMedia "Creating AudioQueue … sampleRate"), which needs a non-sandboxed app and an admin user. For catalog-level flags, MusicKit `Song.audioVariants` (macOS 13+) and the TIDAL v2 API `mediaTags` (LOSSLESS / HIRES_LOSSLESS / DOLBY_ATMOS) work. Roon's public API exposes only display strings, with no signal path.

### Cited Findings
**Apple Music**
- Music.app's AppleScript dictionary on macOS 26.6 defines, on track: `sample rate` ("the sample rate of the track (in Hz)", read-only), `bit rate` ("the bit rate of the track (in kbps)"), `kind`, `cloud status`, `media kind`, `favorited`, `lyrics` ("the lyrics of the track"), and `persistent ID`. On application: `player state` and `player position` — [local sdef inspection of /System/Applications/Music.app/Contents/Resources/com.apple.Music.sdef, macOS 26.6 25G72]
- LosslessSwitcher (GPL-3.0, 2.0k stars, last push 2026-06-07) works by: "Read Apple Music's logs to know the song's sample rate." It "is not, and cannot be sandboxed", and "The user running LosslessSwitcher must be an admin" (because of the OSLog API). The 1.x line works up to macOS 15.3.1; 2.0 beta is for macOS 15.4+ — [vincentneo/LosslessSwitcher](https://github.com/vincentneo/LosslessSwitcher)
- Implementation: `OSLogStore.local()` with the last 5 s of entries and predicate `(subsystem = com.apple.Music | com.apple.coreaudio | com.apple.coremedia) AND (process = "Music")`. It parses `asbdSampleRate = … kHz`, lines from `ACAppleLosslessDecoder.cpp` with "Input format:" (sample rate in "ch, … Hz" and bit depth "from N-bit source"), and CoreMedia "Creating AudioQueue … sampleRate:". A code comment says CoreMedia "don't provide bit depth". The README warns of extra battery use from "frequent querying" — [Console.swift](https://github.com/vincentneo/LosslessSwitcher/blob/main/Quality/Console.swift); [CMPlayerStuff.swift](https://github.com/vincentneo/LosslessSwitcher/blob/main/Quality/CMPlayerStuff.swift)
- LosslessSwitcher 1.1 exposed its own AppleScript so third-party scripts can read the latest detected sample rate — [Softpedia changelog](https://mac.softpedia.com/progChangelog/LosslessSwitcher-Changelog-143188.html)
- Apple's tiers: Lossless up to 24-bit/48 kHz, Hi-Res Lossless up to 24-bit/192 kHz. Apple Music on macOS does not switch the output device's rate on its own — [Apple Support 118295](https://support.apple.com/118295); [Apple Discussions](https://discussions.apple.com/thread/256138473)
- MusicKit `Song.audioVariants` — "The variants that indicate the quality of audio available for the song", available on macOS 13.0+ — [Apple docs](https://developer.apple.com/documentation/musickit/song/audiovariants)
- Lyric Fever uses "private APIs to get the currently playing Apple Music song's iTunes ID, and use MusicKit to map that to an ISRC code" — [aviwad/LyricFever](https://github.com/aviwad/LyricFever)
- Apple Music motion artwork: a (2021-era) Apple staff forum reply said `editorialVideo` is not available to third-party apps through the Apple Music API — [Apple Developer Forums 696843](https://developer.apple.com/forums/thread/696843). Lyrimuse shows "moving album art when Apple Music has a motion cover for the record" and "the song's looping Spotify Canvas video". It does not say which endpoint it uses — [lyrimuse README](https://github.com/Yudaotor/lyrimuse)

**Spotify**
- Spotify's AppleScript dictionary exposes `current track` (name, artist, album, album artist, disc/track number, duration, played count, `starred`, `id`, `artwork url`, `spotify url`), `player state`, `player position`, `sound volume`, `shuffling`, and `repeating`. There is no codec, bitrate or quality property — [local sdef inspection of /Applications/Spotify.app/Contents/Resources/Spotify.sdef]
- Spotify Web API Development Mode changes (announced 2026-02-06): the app owner needs Premium, one Dev-Mode Client ID per developer (raised to 25 in July 2026), up to 5 authorized users per Client ID, and a reduced endpoint set for new apps. Existing apps moved to the new rules on 2026-03-09 (endpoint restrictions for existing apps were postponed) — [Spotify developer blog](https://developer.spotify.com/blog/2026-02-06-update-on-developer-access-and-platform-security); [Migration guide](https://developer.spotify.com/documentation/web-api/tutorials/february-2026-migration-guide); [July 2026 changelog](https://developer.spotify.com/documentation/web-api/references/changes/july-2026); [TechCrunch](https://techcrunch.com/2026/02/06/spotify-changes-developer-mode-api-to-require-premium-accounts-limits-test-users/)
- Extended Quota (since March 2025) requires a registered business, 250k MAU, presence in key markets, and a launched service — [Spotify developer blog via search summary](https://developer.spotify.com/blog/2026-02-06-update-on-developer-access-and-platform-security)

**TIDAL, Qobuz, Deezer, YouTube Music**
- TIDAL's developer platform is a JSON:API at `openapi.tidal.com/v2`. Tracks carry a `mediaTags` string array, and clients show values `LOSSLESS` and `HIRES_LOSSLESS`. The `audioQuality` field elsewhere uses `HI_RES_LOSSLESS`, so handle both spellings. Atmos tracks are reported to carry `DOLBY_ATMOS`. These come from unofficial clients and mirrors, so check them against the official reference — [minim TIDAL docs](https://minim.readthedocs.io/en/dev/api-ref/minim.api.tidal.TracksAPI.html); [tidalrs source](https://docs.rs/crate/tidalrs/0.4.0/source/src/track.rs); [api-evangelist/tidal](https://github.com/api-evangelist/tidal)
- Sleeve says TIDAL, Deezer, SoundCloud and YouTube Music are unsupported because "none of those… ship apps that support AppleScript" — [Sleeve troubleshooting](https://replay.software/help/sleeve/troubleshooting)
- The TIDAL desktop app's MediaRemote metadata mixes the previous and next track when tracks change (an adapter workaround exists) — [mediaremote-adapter README](https://github.com/ungive/mediaremote-adapter)

**Roon**
- node-roon-api is Apache-2.0 (155 stars, last push 2026-02-03). It uses an extension model where an extension pairs with the Roon Core. The transport service's zone `now_playing` has `seek_position`, `length`, `image_key`, and `one_line`/`two_line`/`three_line` display strings, plus zone settings (loop, shuffle, auto_radio), queue info and volume. There are NO signal-path, sample-rate or bit-depth fields — [RoonLabs/node-roon-api](https://github.com/RoonLabs/node-roon-api); [node-roon-api-transport lib.js](https://github.com/RoonLabs/node-roon-api-transport) (Apache-2.0, last push 2020)
- There is a Rust port (TheAppgineer/rust-roon-api, MIT) and an unofficial reverse-engineered client for the private desktop protocol (arthursoares/roon-api-reverse-engineering, MIT, "Unofficial, not affiliated with Roon Labs") — [GitHub search](https://github.com/TheAppgineer/rust-roon-api); [arthursoares/roon-api-reverse-engineering](https://github.com/arthursoares/roon-api-reverse-engineering)

**Other players**
- LyricsX's MusicPlayer library (MPL-2.0) supports Apple Music/iTunes, Spotify, Vox, Audirvana and Swinsian on macOS through scripting — [ddddxxx/MusicPlayer](https://github.com/ddddxxx/MusicPlayer)
- Plex: audio `Stream` elements in Plex XML carry `codec`, `bitDepth` and `samplingRate`, but `bitDepth` may be missing for 16-bit tracks. `/status/sessions` reports Plexamp sessions, playback state, item and position. No official doc confirms the format fields in session output — [Plex forum: codec badging](https://forums.plex.tv/t/codec-badging-in-plexamp-bug/918911); [Symfonium forum](https://support.symfonium.app/t/inconsistent-bit-depth-sample-rate-displyed/14368); [Plex forum feature request 2026](https://forums.plex.tv/t/feature-request-supported-server-mediated-api-for-controlling-remote-plex-plexamp-sessions/942315.md); [python-plexapi audio](https://python-plexapi.readthedocs.io/en/stable/_modules/plexapi/audio.html)

### Inferences
- Plan for three tiers of "quality" display: (1) **Measured** — the actual stream format, from Apple Music logs (LosslessSwitcher technique; admin user, not sandboxed, battery cost) or, for any app, the format of the process-tap stream (this shows the mixer/output format, not the source file). (2) **Catalog** — Lossless / Hi-Res / Atmos badges from MusicKit `audioVariants` (needs the Apple Music song ID, for example through the Lyric Fever-style private iTunes-ID lookup or a catalog search by ISRC), TIDAL `mediaTags`, Plex `Stream` attributes, and the Music.app AppleScript `sample rate`/`bit rate` for local library files. (3) **Unknown** — Spotify, browser tabs, Roon (Roon's own UI shows signal path, but its API doesn't).
- Replay gain and MQA: no source found that exposes these from any of the integrations studied. Treat them as unavailable unless you read local file tags yourself.
- The Spotify Web API is only practical for an open-source desktop app if each user brings their own Client ID (Premium required, up to 5 users). Local AppleScript stays the main Spotify control channel.

### Gaps
- It was not tested whether Music.app's AppleScript `sample rate`/`bit rate` return real values for streamed (non-library) Apple Music tracks on macOS 26/27. The fact that LosslessSwitcher relies on logs suggests they don't.
- No verified integration surface was found for Qobuz desktop, Deezer desktop, foobar2000 for Mac, Doppler (beyond Sleeve support) or Audirvana's current AppleScript properties (format fields).
- Official TIDAL v2 enum values were not confirmed from tidal-music.github.io/tidal-api-reference.
- Whether the Apple Music log line formats survive on macOS 26/27 was not verified, though LosslessSwitcher 2.0 beta targets 15.4+.
- The browser MediaSession API carries no audio-format fields (common knowledge, not sourced here). No source was retrieved on how Lyrimuse's browser pairing works (extension vs. AppleScript JavaScript injection).

## 3. Visualization: spectrum, VU, waveform, album-art color, animated artwork

### Takeaway
Real audio-reactive visuals need system or per-process audio capture through Core Audio process taps (macOS 14.2/14.4+, `NSAudioCaptureUsageDescription` permission), then vDSP FFT and Metal/Core Animation rendering. The most popular notch app, boring.notch, does NOT do this: its "visualizer" bars animate to random values. Good open-source references are insidegui/AudioCap (BSD-2-Clause) for tap setup, projectM (LGPL-2.1) for Milkdrop-style visuals, and ColorKit (MIT) for album-art palettes.

### Cited Findings
- boring.notch `MusicVisualizer.swift`: `let targetScale = CGFloat.random(in: 0.35 ... 1.0)`, animated at 24 fps with `CABasicAnimation`. It is decorative, not audio-reactive. The repo also contains `boringNotch/metal/visualizer.metal` and `AudioPlayer.swift` — [boring.notch MusicVisualizer.swift](https://github.com/TheBoredTeam/boring.notch/blob/main/boringNotch/components/Music/MusicVisualizer.swift); [repo tree](https://github.com/TheBoredTeam/boring.notch)
- AudioCap (BSD-2-Clause, 513 stars, last push 2025-08-07): "With macOS 14.4, Apple introduced new API in CoreAudio that allows any app to capture audio from other apps or the entire system". The permission string is `NSAudioCaptureUsageDescription`, and "There's no public API to request audio recording permission or to check if the app has that permission". The steps are: PID → `kAudioHardwarePropertyTranslatePIDToProcessObject` → `CATapDescription` → `AudioHardwareCreateProcessTap` → private aggregate device with `kAudioAggregateDeviceTapListKey` → read `kAudioTapPropertyFormat` → `AudioDeviceCreateIOProcIDWithBlock` → `AVAudioPCMBuffer` — [insidegui/AudioCap](https://github.com/insidegui/AudioCap)
- projectM: "Cross-platform Music Visualization Library. Open-source and Milkdrop-compatible", LGPL-2.1, 4.6k stars, active (last push 2026-11-20) — [projectM-visualizer/projectm](https://github.com/projectM-visualizer/projectm)
- Small recent Core-Audio-tap visualizers you can study (low maturity): orioshavfx/sysviz (MIT, "macOS cava alternative… (Core Audio tap)"), gabeelezaj/macos-audio-visualizer (MIT), jasas1/Joseon (GPL-3.0, "Swift + Metal: spectrum, spectrogram, loudness, stereo field"), wafiqhsn/Spectrum (no license, "Core Audio Process Tap, Accelerate") — [GitHub search](https://github.com/orioshavfx/sysviz); [gabeelezaj/macos-audio-visualizer](https://github.com/gabeelezaj/macos-audio-visualizer); [jasas1/Joseon](https://github.com/jasas1/Joseon); [wafiqhsn/Spectrum](https://github.com/wafiqhsn/Spectrum)
- Album-art colors: Lyric Fever's "fullscreen view uses a custom mesh gradient and extracts colors from the album art using ColorKit" (aviwad/ColorKit-macOS port, MIT; upstream Boris-Em/ColorKit, MIT). It also uses Spotify's per-lyric "background color" — [LyricFever README](https://github.com/aviwad/LyricFever); [Boris-Em/ColorKit](https://github.com/Boris-Em/ColorKit); [aviwad/ColorKit-macOS](https://github.com/aviwad/ColorKit-macOS)
- boring.notch keeps an `avgColor` (average album-art color) in `MusicManager` — [MusicManager.swift](https://github.com/TheBoredTeam/boring.notch/blob/main/boringNotch/managers/MusicManager.swift)
- Animated artwork: Apple's Music API historically does not expose `editorialVideo` to third parties (2021 staff reply) — [Apple Developer Forums 696843](https://developer.apple.com/forums/thread/696843). Lyrimuse nonetheless shows Apple Music motion covers and Spotify Canvas loops (method not documented) — [lyrimuse README](https://github.com/Yudaotor/lyrimuse)

### Inferences
- An audiophile spectrum/VU in the notch needs: a process tap on the active player's PID (from MediaRemote `processIdentifier`/bundle ID) or a global tap; a ring buffer; vDSP real FFT (`vDSP.FFT`/`vDSP_DFT`) with a Hann window, log-frequency binning and peak-hold; and Metal or CALayer rendering capped at the display rate. The same tap buffer can feed ShazamKit (Section 5). The tap requires the system-audio-recording TCC permission, a UX cost.
- A tap reports the post-mixer format, so a spectrum's upper band edge (for example 96 kHz content) only shows if the device runs at that rate. Don't present tap format as "source quality".
- Motion artwork through private Apple Music endpoints carries ToS and breakage risk. Treat it as optional.

### Gaps
- No official Apple doc on the current state of `editorialVideo` / motion artwork in the Apple Music API in 2026 was retrieved.
- vDSP/Metal performance figures for a always-on notch visualizer (CPU/battery) were not found.
- No source on whether cava officially supports macOS Core Audio taps.

## 4. Lyrics: sources, terms, word-level sync, legal considerations, open-source apps

### Takeaway
LRCLIB is the only clean, open, no-key source of line-synced lyrics. It now also offers word-level timing through "Lyricsfile" (`hasWordSync`), with documented per-IP rate limits and a required User-Agent, but it states no license for the lyrics text. Word-level (karaoke) lyrics otherwise come from Apple Music's private `syllable-lyrics` TTML endpoint (needs a subscriber's Music-User-Token), Spotify's private color-lyrics endpoint (Musixmatch-backed; needs the user's `sp_dc` cookie plus a TOTP secret scraped from the web player, so it is fragile), and Chinese services (NetEase, QQ, Kugou) used by LyricsX and Lyrimuse. Musixmatch's official API and Genius are not usable for full lyrics without a commercial license.

### Cited Findings
**LRCLIB**
- Base `https://lrclib.net`, no API key, CORS enabled. `GET /api/get` (required `track_name` and `artist_name`; `album_name` and `duration` recommended; duration match "±2 seconds"), `GET /api/get/{id}`, `GET /api/search` (up to 20 results), `POST /api/publish` (proof-of-work token via `/api/request-challenge`), `POST /api/flag`, `GET /api/v2/search` (beta) — [LRCLIB docs](https://lrclib.net/docs)
- Fields: `syncedLyrics` (LRC line timestamps), `plainLyrics`, `instrumental`, `hasWordSync`, `lyricsfile` (YAML). "Word-level timings come from Lyricsfile documents, not enhanced LRC", with `hasWordSync` true when `lyricsfile` contains `lines[].words` — [LRCLIB docs](https://lrclib.net/docs)
- Rate limits ("not part of the API contract"): about 45 req/min per IP for generic clients, about 90 for identified clients (User-Agent), about 180 per IP plus about 6,000 app-wide for registered client apps (`Lrclib-App-Id`), and about 6,000 app-wide for registered server apps (`Lrclib-Api-Key`). Clients "must" honor `Retry-After` on 429 and send requests sequentially with a 200–500 ms gap. "We require you to identify your client in requests" (app name, version, homepage/email) — [LRCLIB docs](https://lrclib.net/docs)
- The docs state no license or terms for the lyrics data — [LRCLIB docs](https://lrclib.net/docs). The server code is MIT (tranxuanthang/lrclib, 2.3k stars, last push 2026-11-10) — [tranxuanthang/lrclib](https://github.com/tranxuanthang/lrclib)
- Older 2024-era docs claimed "no rate limiting", which is now outdated — [osdlyrics issue #146](https://github.com/osdlyrics/osdlyrics/issues/146)

**Apple Music TTML / syllable lyrics**
- A community library calls `GET https://amp-api.music.apple.com/v1/catalog/{cc}/songs/{id}/syllable-lyrics` with `Authorization: Bearer` (developer token) and a `Music-User-Token` header, described as "a private, undocumented Apple API. Format may change." The TTML has syllable spans, and word boundaries come from whitespace between spans — [rryam/MusanovaKit](https://github.com/rryam/MusanovaKit); [LyricaAME-py](https://codeberg.org/willooper/LyricaAME-py)
- Music.app's AppleScript `lyrics` property returns plain (unsynced) lyrics for the current track. boring.notch prefers it for Apple Music and then falls back to an LRCLIB `/api/search` — [local sdef inspection]; [boring.notch MusicManager.swift](https://github.com/TheBoredTeam/boring.notch/blob/main/boringNotch/managers/MusicManager.swift)
- Lyrimuse: "Apple Music's lyrics if you connect your account in Settings. Apple Music's lyrics need a subscription, and many of its tracks have word timing" — [lyrimuse README](https://github.com/Yudaotor/lyrimuse)

**Spotify (unofficial)**
- Lyric Fever (MIT, 644 stars, last push 2026-04-03) gets lyrics "from Spotify, LRCLIB, and NetEase as a backup" and maps Apple Music songs to Spotify IDs by ISRC. Its Spotify provider gets a web-player token from `https://open.spotify.com/api/token?reason=init&productType=web-player&totp=…&totpVer=5…`, sending the user's cookie `sp_dc=…`. The TOTP secret is fetched at runtime from `https://iloveyoulyricfever.github.io/myloveisasecret/mylove.json`, which shows the secret rotates and has to be re-scraped — [aviwad/LyricFever](https://github.com/aviwad/LyricFever); [SpotifyLyricProvider.swift](https://github.com/aviwad/LyricFever/blob/main/LyricFever/LyricProvider/Spotify/SpotifyLyricProvider.swift)
- Lyric Fever needs macOS Sequoia+, uses ScriptingBridge for Spotify/Apple Music and Apple's on-device Translation API, and claims "0.1% CPU usage of Lyric Fever vs 3% of LyricsX" (developer's own claim) — [LyricFever README](https://github.com/aviwad/LyricFever)

**Musixmatch, Genius**
- Musixmatch's official API terms were not retrievable. Aggregators claim the free tier returns about 30% of lyrics and that full or synced lyrics need a commercial license (unverified) — [freeapihub](https://freeapihub.com/apis/musixmatch); [lib.rs musixmatch-inofficial](https://lib.rs/crates/musixmatch-inofficial)
- The official Genius API "does not provide lyrics due to legal restrictions". Wrappers scrape genius.com pages, which "may violate Genius' terms of service" — [lyricsgenius docs](https://docsearch.algolia.com/mcp/docs/repo/johnwmillr/lyricsgenius); [johnwmillr blog](https://johnwmillr.github.io/scraping-genius-lyrics/)

**LyricsX / LyricsKit and Lyrimuse**
- LyricsX (MPL-2.0, 5.3k stars, last push 2026-07-22). It uses the "LRCX" format, which supports "word time tag, multi-language translation" and is LRC-compatible, and gets players through ddddxxx/MusicPlayer (MPL-2.0) — [ddddxxx/LyricsX](https://github.com/ddddxxx/LyricsX)
- LyricsKit (MPL-2.0, last push 2024-02-17) providers: NetEase, QQMusic, Kugou, Gecimi, Syair; discontinued: ViewLyrics, Xiami — [ddddxxx/LyricsKit tree](https://github.com/ddddxxx/LyricsKit)
- Lyrimuse (GPL-3.0) uses "Sixteen lyrics sources": NetEase, QQ Music, Kugou, Kuwo, Migu, LRCLIB, LyricFind (through YouTube Music), Deezer, AMLL ("a hand-curated word-by-word lyrics database"), Soda Music, VIBE, Genie, PetitLyrics, Zing MP3, Megalobiz, and Apple Music. Features include word-by-word highlighting, duet splitting, a "Dynamic-Island-style capsule under the notch", and on-device Translation framework romanization — [Yudaotor/lyrimuse](https://github.com/Yudaotor/lyrimuse)

### Inferences
- Legal posture for an open-source app: lyrics text is copyrighted (publishers). The safest design is one where the app fetches on the user's device from sources the user chooses (LRCLIB by default; Apple Music syllable lyrics and Spotify lyrics only with the user's own credentials, opt-in, clearly labeled "unofficial"). Never cache or redistribute lyrics on a project server, and never bundle lyrics. Scraped sources (Genius, Chinese services, Spotify) carry ToS and breakage risk. Lyric Fever's need to keep re-scraping a rotating TOTP secret shows the maintenance burden.
- To be a good LRCLIB citizen: set a descriptive User-Agent, register an `Lrclib-App-Id`, serialize requests, cache locally, and always send `duration` to get the ±2 s match.
- Word-level sync sources, best first: Apple Music TTML (subscriber), Spotify (user cookie), LRCLIB Lyricsfile (where `hasWordSync`), and AMLL/NetEase/QQ (strong for Asian catalogs).

### Gaps
- Official Musixmatch developer terms and current pricing were not retrieved.
- The LRCLIB data license or contributor terms are not stated in the API docs. It is not confirmed whether database dumps exist or what license they carry.
- AMLL's license and the Apple Music TTML endpoint's ToS status were not checked.
- No legal precedent specific to open-source lyric display apps was found.

## 5. Music recognition: ShazamKit (system audio and mic) and alternatives

### Takeaway
ShazamKit is the best default. `SHSession.matchStreamingBuffer(_:at:)` (macOS 12+) accepts any `AVAudioPCMBuffer`, so process-tap system audio can be fed straight in. `SHManagedSession` (macOS 14+) records the mic itself and "won't accept audio or Signatures that it didn't generate." Using the Shazam catalog requires enabling the ShazamKit App Service on the App ID. Under the App Sandbox it works as long as the main executable links ShazamKit (a July 2026 DTS thread). No pricing or rate limits are published. Open alternatives: AcoustID/Chromaprint (free only for non-commercial use, 3 req/s, built for whole files), AudD ($2–5 per 1,000 requests, 300 free), ACRCloud (pricing behind login), and self-hosted fingerprinting (Dejavu MIT, Panako/Olaf AGPL-3.0) that only matches your own indexed catalog.

### Cited Findings
**ShazamKit**
- `SHSession` (macOS 12.0+): "Call `matchStreamingBuffer(_:at:)` with a streaming audio buffer, and ShazamKit generates the signature for you", or build an `SHSignature` with `SHSignatureGenerator.append(buffer, at:)` and call `match(_:)` / `result(from:)`. It also has a `results` async sequence. "Matching audio against the Shazam catalog requires enabling your app to access the catalog. If you are using a custom catalog, you don't need to enable ShazamKit" — [Apple docs: SHSession](https://developer.apple.com/documentation/shazamkit/shsession)
- `SHManagedSession` (macOS 14.0+) "performs all recording of audio and signature generation" and "won't accept audio or Signatures that it didn't generate". It has `prepare()`, `result()`, `results`, `state`, and `cancel()` — [Apple docs: SHManagedSession](https://developer.apple.com/documentation/shazamkit/shmanagedsession)
- Enabling: Certificates, Identifiers & Profiles → App ID → App Services tab → "Select the ShazamKit checkbox". The page does not mention cost, rate limits or Developer ID — [Apple: Enable ShazamKit for an App ID](https://developer.apple.com/help/account/configure-app-services/shazamkit)
- Sandbox, macOS 26.1 (July 2026 forum thread): sandboxed builds got "com.apple.ShazamKit error 202 — The connection to service named com.apple.shazamd was invalidated", with `deny(1) mach-lookup com.apple.shazamd`. DTS (Quinn): "if the app links to the ShazamKit framework, App Sandbox extends its sandbox to allow that lookup". The developer's fix: "link ShazamKit in the main app and drop the temporary-exception". The iOS entitlement `com.apple.developer.shazamkit` "is rejected by the macOS validator at upload". The thread does not cover non-sandboxed or Developer ID builds — [Apple Developer Forums 837008](https://developer.apple.com/forums/thread/837008)
- Known problems: an `NSException` sometimes thrown by `matchStreamingBuffer` with PCM buffers ([forum 731191](https://developer.apple.com/forums/thread/731191)), and `SHManagedSession` not working on macOS 14 RC (2023, older) ([ShazamKit forum tag](https://developers.apple.com/forums/tags/shazamkit))
- The WWDC21 pattern: tap the input node and pass each buffer plus its `AVAudioTime` to `matchStreamingBuffer` — [WWDC21 10045](https://developer.apple.com/videos/play/wwdc2021/10045)

**AcoustID / Chromaprint**
- AcoustID web service: "This service is provided for free for non-commercial use only". Commercial use goes through a separate sign-up (AcoustID OÜ). "Do not make more than 3 requests per second." Application registration is required for an API key. `/v2/lookup` takes `fingerprint`, `duration` ("duration of the whole audio file in seconds") and `meta=recordings+releasegroups`, and returns MusicBrainz IDs — [acoustid.org/webservice](https://acoustid.org/webservice)
- Chromaprint: its own code is MIT but includes FFmpeg parts (LGPL-2.1), "As a whole, Chromaprint should be therefore considered to be licensed under the LGPL 2.1 license". Linking FFTW3 makes the binary GPL. The GitHub API reports `NOASSERTION`; 1.4k stars; last push 2026-10-15 — [acoustid/chromaprint README](https://github.com/acoustid/chromaprint/blob/master/README.md)

**Commercial APIs**
- AudD: "from $2 to $5 per 1000 requests"; $450/month for 100k, $850 for 200k (a third-party source says $800), $1,800 for 500k; "First 300 requests for free"; streams $45/stream/month; claims a "DB contains 160 million songs" and recognition of "short clips… through background noise". Results include `song_link`, plus Apple Music and Spotify IDs with `return=apple_music,spotify`. ISRC/UPC require a "Startup plan or higher". These are vendor claims — [audd.io](https://audd.io/); [itechguides](https://www.itechguides.com/products/audd/)
- ACRCloud: pricing is only shown in the logged-in console. A free trial needs no credit card. The only per-request figure found ($5.8 per 1,000) is from a 2019 forum post and is outdated — [acrcloud.com](https://www.acrcloud.com); [dBpoweramp forum (2019)](https://forum.dbpoweramp.com/forum/other-topics/wishlist/39494-acrcloud-recognition-and-metadata)

**Open-source fingerprinting (self-hosted, own catalog only)**
- worldveil/dejavu: MIT, 6.8k stars, last push 2024-04-22 (dormant) — [GitHub API](https://github.com/worldveil/dejavu)
- JorenSix/Panako: AGPL-3.0, last push 2026-09-17. JorenSix/Olaf ("Overly Lightweight Acoustic Fingerprinting", portable): AGPL-3.0, last push 2026-10-16 — [Panako](https://github.com/JorenSix/Panako); [Olaf](https://github.com/JorenSix/Olaf)

### Inferences
- Pipeline: process tap (or mic via AVAudioEngine) → convert to mono float PCM → push about 3–12 s into `SHSession.matchStreamingBuffer`, or into `SHSignatureGenerator` then `result(from:)` → show `SHMatchedMediaItem` (title, artist, artwork, Apple Music URL, ISRC) → optionally look up `audioVariants`. Ship a non-sandboxed Developer ID build that links ShazamKit in the main binary, with the App ID's ShazamKit service enabled.
- System-audio recognition is mostly redundant when MediaRemote already gives the title. It matters for players without metadata (DJ mixes, live streams, Twitch/YouTube videos, untagged files) and for "what's this sample" moments. Mic recognition covers the room (vinyl, radio).
- AcoustID's whole-file `duration` model and Chromaprint's design make it a poor fit for 10-second live/mic snippets. It is better for tagging local files. Its non-commercial-only terms suit a free open-source app.
- Panako and Olaf are AGPL-3.0, so linking them would force the whole app to AGPL. They only match catalogs you index yourself.

### Gaps
- No official ShazamKit rate limits, quotas or pricing were found (it appears free with the developer program, but that is not documented on the pages retrieved).
- No primary confirmation was found that a Developer ID (non-App Store) macOS app can use the Shazam catalog, though App-ID-based enabling suggests it can.
- No documentation on ShazamKit's accepted buffer formats (sample rates/channels) for `matchStreamingBuffer` was retrieved.
- There is no public API to read or write the Control Center "Music Recognition" / Shazam history from a third-party app (`SHLibrary` docs were not retrieved).
- No independent accuracy benchmarks (mic vs. clean digital tap; ShazamKit vs. AudD vs. ACRCloud) were found.

## 6. Scrobbling and listening history (Last.fm, ListenBrainz)

### Takeaway
ListenBrainz is the open option: a token-authenticated JSON API (`POST /1/submit-listens` with `playing_now`/`single`/`import`), listen data released as CC0, and MusicBrainz IDs. Last.fm's Scrobbling 2.0 (`track.updateNowPlaying` + `track.scrobble`) is fine for a free open-source app, but its API ToS limits use to non-commercial purposes unless you sign a separate agreement.

### Cited Findings
- ListenBrainz: `POST /1/submit-listens` with a user token (from the settings page) in the `Authorization` header. "Playing Now listens are only stored temporarily" and must be resubmitted as `single`/`import` for permanent storage. `return_msid` gives a `recording_msid` for love/hate feedback — [ListenBrainz API core docs](https://listenbrainz.readthedocs.io/en/latest/users/api/core.html); [JSON docs](https://listenbrainz.readthedocs.io/en/latest/users/json.html)
- ListenBrainz data is CC0 (public dumps) — [Zenodo dataset paper](https://zenodo.org/record/14877361/files/000044.pdf); [alternativeto/ListenBrainz](https://alternativeto.net/software/listenbrainz/about)
- Last.fm API ToS: use of Last.fm data "is limited to non-commercial purposes"; commercial use requires an agreement (partners@last.fm). Scrobbling 2.0: clients should send `track.updateNowPlaying` and `track.scrobble`; now-playing is optional but recommended; accounts may be suspended for excessive call rates — [Last.fm API ToS](https://www.last.fm/api/tos); [Scrobbling 2.0](https://www.last.fm/api/scrobbling); [track.updateNowPlaying](https://www.last.fm/api/show/track.updateNowPlaying); [API intro](https://last.fm/api/intro)
- Existing macOS clients: Sleeve includes Last.fm scrobbling (per an older linklog); Lyrimuse "keeps a Last.fm listening profile and scrobbles your plays" — [pxlnv linklog](https://pxlnv.com/linklog/sleeve-for-mac/); [lyrimuse README](https://github.com/Yudaotor/lyrimuse)

### Inferences
- Scrobble from the unified now-playing model (MediaRemote plus per-app channels). Standard rules apply: scrobble after 50% of the track or 4 minutes, and skip `isAdvertisement`. Attach MBIDs when available (from AcoustID/MusicBrainz or ShazamKit ISRC → MusicBrainz lookup) to improve ListenBrainz matching. Keep a local history store (SQLite) as the source for personalization, and treat Last.fm/ListenBrainz as optional sinks.
- With multi-session reading, you can tell which session is "really listened to" (playing + audible), which matters when a muted YouTube tab and Spotify run together.

### Gaps
- No ListenBrainz rate-limit figures were retrieved (rate-limit headers exist but were not checked).
- The exact current "scrobble threshold" text was not re-verified from the Last.fm docs in this session (the 50%/4-minute rule above is standard but unsourced here).
